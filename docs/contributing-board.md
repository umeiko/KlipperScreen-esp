# Contributing a new board (PR guide)

Contributing support for a new board means "one BSP implementation + full plumbing registration". Always start from [`templates/board/`](https://github.com/umeiko/KlipperScreen-esp/tree/main/templates/board); existing BSPs are controller-specific references, not copy bases. Read the [porting guide](porting.md) first.

## Naming convention

Board identifiers are **lowercase snake_case** model names (e.g. `cyd_2432s028r`, `e32r35t`); the Kconfig macro is `CONFIG_BOARD_<UPPER>`. Build artifacts, CI matrix entries and sdkconfig file names all use the same identifier.

## Files to add/modify

| # | File | Change | Required? |
|---|---|---|---|
| 1 | `src/bsp/esp32/bsp_<board>.c` | Copy the board template, then fill only the marked hardware sections; keep the whole file under `#if CONFIG_BOARD_<BOARD>` | ✅ |
| 2 | `src/bsp/Kconfig.projbuild` | Add `config BOARD_<BOARD>` to `choice BOARD` | ✅ |
| 3 | `src/bsp/CMakeLists.txt` | Add the source to SRCS; add the component name to REQUIRES if a new driver chip is used | ✅ |
| 4 | `src/ports/esp32/entry/idf_component.yml` | Add the managed-component dependency with a version constraint if a new driver chip is used | If needed |
| 5 | `src/ports/esp32/sdkconfig.defaults.<board>` | New file: `CONFIG_BOARD_<BOARD>=y` + flash mode/size/CPU freq (copy from a same-chip board and change the macro) | ✅ |
| 6 | `tools/build-esp32.sh` | Add a case to `board_conf()` (TARGET/BDIR/SDKCFG/DEFS), add to the `all` branch, update the header comments | ✅ |
| 7 | `.github/workflows/build.yml` | Add an entry to the `firmware` matrix (board/target/bdir/sdkcfg/defs/chip/flash_size/bl_offset) and one to the `package` matrix | ✅ |
| 8 | `src/ui/ui_layout.c` | Add `#elif defined(CONFIG_BOARD_<BOARD>)` to the font-tier selection | ✅ |
| 9 | `README.md` / `README_zh.md` | Add the board to the supported-boards list (with status) | ✅ |
| 10 | `docs/boards.md` / `docs/boards.zh.md` | Hardware info and pinout tables (the "Supported boards" page of this site) | ✅ |
| 11 | `src/ports/esp32/partitions_<board>.csv` | Only if the flash layout differs from the default `partitions.csv` | If needed |
| 12 | `src/ports/esp32/sdkconfig.<board>` | The full sdkconfig generated by the first build; committing it is recommended (same precedent as jc8048w550) to avoid drift if CI regenerates it | Recommended |

## Rules and pitfalls

- **No per-board source filtering**: all board sources in `src/bsp/CMakeLists.txt` are always compiled and selected via in-file `#if CONFIG_BOARD_*`. Component registration happens before kconfig loads, so `if(CONFIG_...)` cannot work at the CMake level.
- **New boards are always WIP**: set `suffix: "-WIP"` in the CI `package` matrix, and mark WIP in the READMEs and the boards page. Remove the flag only after on-device validation.
- **WIP note text**: the WIP.txt step in the workflow generates its text from `matrix.board` — nothing extra to change.
- **Bootloader offset**: ESP32/ESP32-S3 use `bl_offset: 0x1000`; chips with the newer boot chain (C3 etc.) use `0x0`.
- **Both READMEs**: `README.md` and `README_zh.md` must be updated together.

## Verification before submitting

1. Full local build of the new board passes: `bash tools/build-esp32.sh <board>`
2. **Regression build** of at least one existing board (mandatory when shared files changed): `bash tools/build-esp32.sh cyd_2432s028r`
3. Firmware size check: the `binary size` printed at the end of the build fits the app partition (currently 0x320000)
4. Run the porting guide's five-colour test without LVGL, then verify the boot animation, full UI, and every declared input
5. If no hardware was tested, state "not tested on hardware" explicitly and keep the board marked WIP

## What to include in the PR

- Board documentation links (vendor wiki / schematic / pinout table)
- Display interface class (SPI/I80/RGB/QSPI/MIPI), controller, and proven clock or timing values
- On-device photos or logs for both the five-colour test and full UI — or an explicit note that they are untested
- Intentional deviations from the template BSP (e.g. shared bus, no RST pin, forced calibration) to ease review
- Input declaration: touch, rotary, both, or neither. Rotary GPIOs belong in Kconfig/sdkconfig rather than a private UI implementation

Commit message style (see history): `feat: add <board> support (<display> + <touch/rotary>, WIP)`.
